New compactor: two phases, it sorts the pools in such way that compaction happens in the direction of being able to free chunks of pools. (Chunks are large numbers of pools.) Whole chunks that are free are given back to the OS. Otherwise it's kind of the same.

### Backup threads

Nick: whenever an OCaml program enters a blocking section, for example reading a byte from a file, it releases its domain lock which has the effect that a backup thread for that domain gets control, and then wait. The main thread finishes and asks for the domain lock, but the backup thread is still waiting for something to do. This is bad.

The backup thread exists to service GC requests. The obviously better thing to do is to pay the price when you want to do a GC: if another domain is in a blocking section, then its backup thread should be woken up.

Gabriel: so how does the synchronization work?

Stephen: you wake the backup thread when you initialize it. Use a pthread condition variable.

Nick: Python has a global interpreter lock, we have a domain lock, they need to work nicely together.

Gabriel asks about the scary piece of code that tries to interrupt all domains while being async-safe for signal stuff. Stephen has not touched that part, only the interruption logic within the STW runner.

Gabriel: So it looks like the change is not that large. You could send it upstream whenever you want.

Stephen: not planning to upstream it immediately, but it would be nice to get it into 5.5.

The loop in [`caml_plat_spin_back_off`](https://github.com/ocaml/ocaml/blob/61104576261fe2eae8a7a2543bceaf9fe8904b83/runtime/platform.c#L476-L495) accounts for waiting time in nanoseconds, which means that any time below 1ms is equivalent to calling `Sleep(0)`, which relegates the calling process at the end of the process queue. Any increment below 1ms is also lost. We can imagine that for short or tight loops (spin wait, game loops) a better precision would be welcome. Windows has introduced timer handles (like _timerfd_ on Linux) that have a 100ns resolution. The timer can be created once and rearmed. The timer cannot live in the domain state, as if the runtime system is released, it won't be valid to access the timer. IIUC, the backup thread and the sysstread's tick thread might want to sleep too. The timer cannot live in a syssthread struct, as it won't be accessible from the runtime or from the unix library. It seems that thread-local storage is the right place. I'd like to discuss this design, find the right places where the timer can be created or destroyed, and find convincing examples or test cases. Preliminary work at [Sub-microseconds sleeps on Windows](https://github.com/MisterDA/ocaml/pull/24). May be related to [ Windows threads: maintain a number of threads waiting on the master lock to avoid unnecessary context switches #13847 ](https://github.com/ocaml/ocaml/pull/13847).
