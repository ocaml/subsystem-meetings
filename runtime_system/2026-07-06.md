### Gc.compact/caml_fatal_error and unikernels (Report major-heap fragmentation)

Edwin: Discovered issues with Unikernels running out of memory and not being able to allocate more memory. We don't have any statistics on custom memory usage, the new GC is tracking this usage in bytes.

Stephen: Many libc implementations provide memory fragmentation stats.

Edwin: Could we add this to the GC stats API? We also run into caml fatal error when running out of memory, this occurs when trying to request more memory from the OS, and where memory that is free-d is not immediately available to mmap. malloc_trim helps, although that isn't standard so not something upstream OCaml could do, but can be useful for unikernels. Reserving memory for minor heaps is also useful to prevent the crash in caml_fatal_error, for now I'm trying out the idea in Mirage, but eventually it might be more robust for the runtime to do this in its pool allocator (reserve memory outside of minor heap collections, such that there is at least one more minor heap's worth of memory available, and raise out_of_memory as usual).

Stephen: Do you have a reproduction for this behaviour?

Edwin: The examples are Unikernel specific. Wrote some testcases that try to exercise bad/worst-case behaviours: worst-case fragmentation for a C allocator based on https://sqlite.org/malloc.html#_mathematical_guarantees_against_memory_allocation_failures, and also a TCP windowed allocation/processing/freeing (if the GC isn't keeping up with the pace it'll increase RSS until compaction is run). We could extract this into a micro-benchmark, that demonstrates the worst case behaviour. Provide PRs for next meeting.

Navaneeth: Would automatic compaction help in this case?

Edwin: The 4.14 compactor does, for 5.x it helps with small objects.

Nick: Neither OCaml or OxCaml moves or frees large objects. In the OxCaml compactor, it works hard to keep 32kb pages together.

Navaneeth: Looking for examples that demonstrate Sadiq's OxCaml compactor is an improvement.

Stephen: We should upstream the Huge Page Support. Trunk ocaml call map/munmap too much.

Edwin: https://github.com/ocaml/ocaml/issues/14865 corner case

Nick: Broad goals to converge the OxCaml / OCaml codebases. With the runtime being closer to upstream than other parts of OxCaml. Watch this space!

Tim: Will the runtime parts of region/stack allocation be upstreamed.

Stephen: The region/stack allocation is kept separate. The pieces that should be the same are more of a problem. Small invariants or minor divergences.
