## Unloadable runtime

This is code to make it possible to release all resources (memory, threads, locks, etc) allocated or reserved for OCaml, when the OCaml runtime is no longer required. This allows OCaml components to be used as short-lived parts of a larger and longer-running application process. This feature is present in OCaml 4 but not yet in Ocaml 5. Miod is working to implement it.

Damien mentioned that this was originally developed for Facebook, who have applications exactly fitting that description. In OCaml 4, this isn't too hard. In OCaml 5 it is harder because each domain has responsibility for some resources (memory, threads, locks), but some of these have a lifetime beyond that domain. In particular, a domain's shared heap is orphaned when that domain terminates, and adopted by another domain.

Miod discussed his current work. The existing PRs have gone back into draft mode and he is reworking.

There was a discussion about the expected behaviour at the termination of the main domain, if other domains remain un-joined. Domains are not all first-class citizens: in the standalone runtime, when the main domain terminates, the process calls `exit()` and everything goes away. But it's hard to force the _clean_ exit of an uncooperative thread: `pthread_destroy()` can make it go away but can't make it clean up its resources. Damien points out that the thread may hold a lock, for example. The POSIX standard doesn't give many guarantees, although it's unclear whether actual implementations are helpful or unhelpful here.

Gabriel Scherer has suggested declaring this situation (the exit of the main domain while other domains are un-joined) as "undefined behaviour" which may lead to a crash, although we might attempt to be graceful.

Miod is planning to move this work to a single PR (a previous version has been two PRs) to bring discussion into one place and make merging more likely. Damien points out that if we start with an "undefined behaviour" semantics, then we can refine it later.

## "Compiler Dreams" runtime ideas

Nick explained that last week the Compiler pillar in Tarides engaged in a "Compiler Dreams" workshop, exploring our longer-term ideas for the language without considering time and effort constraints. Several runtime-related ideas were discussed, including these two:

### Oxidation

This is the term for adding some Rust-like object ownership and memory management to OCaml. This is already implemented at Jane Street, and Tarides is likely to be deeply involved in adding these features to upstream OCaml, over the next year or more. It's mainly type system work, but there are runtime aspects, in particular for "local allocation", which is really region allocation.

We discussed the history of region allocation a little. Region inference was originally developed in the 1990s in the ML Kit implementation of Standard ML. At one time that system only had inferred region allocation, with no true GC. That relied on region _inference_, whereas the type modes system at Jane Street has explicit region stacks, and the implementation works closely with the GC.

The Jane Street implementation of local allocation depends somewhat on their Flambda-2 engine, so full upstreaming of it may lag behind that, but we could approach it from both ends, closing the gap between the Jane Street and upstream implementations. This might start by providing the runtime mechanisms on which it will depend, and then wiring those into the various platform backends.

### Pluggable GC

Nick outlined the idea here, of separating the GC implementation from the rest of the runtime in such a way that the GC could be replaced by a third-party system (such as [MMTK](https://www.mmtk.io/) or the [MPS](https://www.ravenbrook.com/project/mps/). This might cause performance degradation, but may be worthwhile for the purpose of experimenting with difference GC approaches.  For example, we could look at mostly-copying GCs (which would tolerate ambiguous stack roots, simplifying the FFI), or generational GCs with larger numbers of generations.

Damien mentions that an aerospace company (Airbus?) has already done a basic version of this for OCaml 4, replacing the incremental GC with a very simple GC, in order to get OCaml-based software components through some sort of certification process. Their implementation is unlikely to be available, but there is some knowledge of it in the runtime community.

Damien also points out that part of the GC interface is defined by the compiler backend - generated code has to follow an ABI to maintain invariants required by the GC, and that ABI is really defined implicitly by the backends (for instance, roots all have to be in well-formed stack frames at GC safe points).

## Runtime Robustness

At Seb's suggestion, Nick gave a quick summary of where we are with the runtime robustness work: new macros are in, including a new `CAMLunreachable` macro to replace `CAMLassert(false)`. Preliminary testing is OK. We've established that no checks are very expensive.

## OCaml 4/5 Runtime shift

Jan asked whether there is more to do to bring the OCaml 5 runtime up to full functional equivalence with OCaml 4 (some features were dropped to get multicore OCaml merged). Statmemprof is done. Damien says that ephemerons might still be reworked - they are used for weak references but that's not very efficient.
