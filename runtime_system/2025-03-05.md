# OCaml Runtime/GC Meeting Notes from 2025-03-05

Approximately every six weeks we have an informal meeting between OCaml developers with a focus on the language runtime. The meetings are for sharing understanding and ideas, not for formal planning purposes. They are open to any interested developer. This document is to collect agenda item suggestions. This document is notes from the meeting held on 2025-03-05 at 11:00 UTC (11:00 London/Cambridge, 12:00 Paris). 

Attendees: Stephen Dolan, Damien Doligez, David Allsopp, Nick Barnes.

Apologies from Nick for late change to the meeting time, which has caused Tim McGilchrist to miss the meeting.

## GC pacing

Stephen and Nick have recently merged a version of Damien's pacing work into the flambda-backend runtime. Stephen showed a graph of true space overhead against requested space overhead for a test program: the new algorithm is clearly much better than either runtime 4 or runtime 5. There was some discussion of the graph. Jane Street are starting to measure the new algorithm with real applications.

Further improvements will be forthcoming: a "square root patch" to adjust the GC intensity depending on the promotion rate (apps with large heaps which enter a phase of very little promotion basically stop major GC work, despite having many GB of old garbage on the heap from the previous cycle).

Also forthcoming, tentatively: changes to the order in which the heap is swept, so that we sweep more garbage sooner. The model assumes that garbage is swept uniformly through the sweeping phase, but a lot of apps with large heaps show a behaviour in which all the garbage is swept at once (presumably because it's clustered by block size?). If this happens late in sweeping then the heap overhead can exceed the parameter.

David asked about upstreaming. We think this should be fairly easy as much of it is a port of Damien's original upstream patch. We should take care to get the public API right as API changes are very expensive for ocaml/ocaml. Some API discussion; obviously this needs more thinking.

Can we identify users of the existing API?

David suggests using something similar to the no-naked-pointers checker used during development of the multicore runtime.

We should probably present something on this at the caml-devel meeting in 3 weeks.

David asks about effects of the pacing change on #11733 (Frama/C) #12929 (compaction?), and #13123. Nick is optimistic that many of the performance problems reported with OCaml 5 will be improved by a combination of these patches, with mark-delay (landed in flambda-backend some time ago but currently stuck in Draft mode upstream because of a niggling problem with finalisers found by multicoretests). Certainly any time/space performance issues upstream will need to be revisited after this lands.
