#### Fix interaction of or-patterns, GADTs and as-patterns

https://github.com/ocaml/ocaml/pull/11799

Jacques would like the following, with extra annotations, to work:

```ocaml
type _ t =
      | A : [ `A ] t
      | B : [ `B ] t

let foo : type a. a t -> a t =
    fun t ->
      match t with
      | ((A : a t) | (B : a t)) as t' -> t'
(* does not work *)

(* or maybe *)
let foo : type a. a t -> a t =
    fun t ->
      match t with
      | ((A | B) : a t) as t' -> t'
(* does not work either *)
```

We would ideally like one eof those versions to work.

The typing rules for `p as x` are currently documented there:

  https://github.com/ocaml/ocaml/pull/1655#issuecomment-648808376
  
  
Typing rule for type annotations:

```
(p : ty) as x
==>
(p as x' : ty) where x = (x' : ty)
```

where the two occurrences of `ty` are different instances

Gabriel: maybe we could change the typing rule for `(p : ty) as x` to be able to propagate an instance of `ty` when type-checking `p`, so that we can work correctly in presence of GADTs under or-patterns.

This corresponds to stopping the generalization process.

Jacques: yes, the type annotation means that you decided that you want that type.

Options considered:

1. At the toplevel of `build_as_type`, if there is a failure when retyping/generalizing the pattern, fall back to the previously inferred type for the pattern.

2. Leo's option: the fallback strategy above, but on each or-pattern instead of at the toplevel.

3. Make `build_as_type` gadt-aware by propagating an expected type that starts absent, and gets populated when encountering a type annotation inside the as-pattern.

4. Merge `build_as_type` with the "normal" type-checking function for patterns by making it return the generalized type. (Idea: 3 makes the implementation of build_as_type almost as complex as the type-checker pass, and (4) avoids a duplication of the same logic in two different functions).

5. Handle ground type annotations specially: in this case we don't even try to generalize the as-pattern type at all, we use the type annotation directly.

Jacques: what I don't like about 1, 2 is that it accepts some code with a "good enough" type, but maybe later we refine the code and we start using a better type, and this breaks compatibility for existing code. On the other hand, 5. does not have this problem: in the case where it works it gives the "best" type, and otherwise we get the current behavior, a type error. (So no code gets written that relies on the type-error behavior.)

Consensus on (5).
