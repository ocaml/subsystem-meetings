### Naming existential variables in GADTs

Jacques: the original feature would let you give names to existentials, that do not appear at all in the return type. You have no way to bind it.

```ocaml
type _ th =
  | Thunk : 'b * ('b -> 'c) -> 'c th

(* this works *)
let f1 (type a) : a th -> a = function
  | Thunk (type b) (x, f : b * (b -> _)) -> f x

(* what about this? *)
let f2 (type a) : a th -> a = function
  | Thunk (type b c) (x, f : b * (b -> c)) -> f x
```

This is easy to implement because the type-checker has a list of those existential types for each constructor. So at this point we decide how to name them. Now if we are talking about some other variables that are created by unification, this is harder to implement.

```ocaml
type _ ty =
  | Int : int ty
  | Pair : 'b ty * 'c ty -> ('b * 'c) ty

(* Gabriel would like this to work *)
let rec example1 : type a . a ty -> a = function
| Int -> 0
| Pair (type b c) (x, y : b ty * c ty) -> (example1 x, example1 y)

(* Jacques mentions that this is a corner case *)
let example2a : (int * int) ty -> unit = function
| Pair (type b c) (x, y : b ty * c ty) -> ()
  (* Leo does not want this: 'b' ought to be "really" abstract, with an equation *)
```

Leo writes:
> I'm fine with the abstract type being equal to types other than existentials outside of its scope, but within its scope it should be abstract.

Gabriel's interpretation: we can introduce `type b = $0` in the context, but not `type b = int`.

```ocaml
(* Richard thinks Leo might not like this: *)
let example3 : (int * int) ty -> int = function
| Pair (type b c) (x, y : b ty * c ty) -> (5 : b)
```

```ocaml
(* Gabriel: what about this? *)
let example2b : type a . (a * a) ty -> unit = function
| Pair (type b c) (x, y : b ty * c ty) -> ()
```

```ocaml
(* Florian's example: *)
let example4 : type b c. ((b*c) ty * (b,c) Type.eq ty ) ty -> b list = function
| Pair (type x y) (x, eq : (x*y) ty * (x,y) Type.eq ty) ->
   let Refl = eq in
   let a, b = x in
   [a;b]
```

Gabriel's proposal: allow the `(type b c)` if the equations they introduce is to a local type introduced by the pattern-matching clause -- a "local type of the clause". I hope that this may make Leo happy, and it gives me the property I want that there are no un-nameable types anymore.

Richard: we could accept example{1,2a,2b} but still reject f2. Or we accept example1, and reject all the others.

Gabriel: accept example1 (Gabriel wants it to be accepted), reject example3 (Leo wants it rejected). In the middle do what is easier/simpler in the code.
