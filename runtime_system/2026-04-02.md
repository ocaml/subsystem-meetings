### Eduardo: fixed heap size

In order to evaluate different GC algorithms, we could have a way to fix the heap size. Eventually if you run out of memory you can measure the amount of memory that you need to execute the program. That way you can compare ... as well. I've been talking to Tim. I was wondering whether we can have something.

Damien: is it just for benchmarking?

Eduardo: you wouldn't use this in the default setting.

Damien: it would be useful to generalize this to have minimum size and maximum size.

Gabriel: Go has a GOMEMLIMIT (soft limit) that they use to improve Gc pacing.

Gabriel: but I don't understand the use-case for benchmarking: if you set the limit you are going to change the pacing completely, and this will impact the performance.

Damien: if we had a limit we could delay GC work until we reach the limit, it may improve performance for some programs (but use more memory).

KC: if your code is doing benchmarking for regular users, but you are benchmarking with respect to the hard limit, it is not going to reflect what the users will see. I would suggest what Damien suggested, which is to vary the space-overhead parameter and use that to measure time and space.

Nick: some STW pauses create overhead.

Damien: an example of varying the overhead parameter
