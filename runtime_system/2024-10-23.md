# OCaml Runtime/GC Meeting Notes from 2024-10-23

Approximately every six weeks we have an informal meeting between OCaml developers with a focus on the language runtime. The meetings are for sharing understanding and ideas, not for formal planning purposes. This document is notes from the meeting held on 2024-10-23 at 09:00 UTC.(10:00 Cambridge, 11:00 Paris), attended by Miod Vallat, Vesa Karvonen, Tim McGilchrist, Antonin Decimo, Fabrice Buoro, Stephen Dolan, Damien Doligez, and Nick Barnes.

## Fiber-local storage

Vesa presented on fiber-local storage. Motivating examples include fiber identity for e.g. mutex owner. Picos implements via an OCaml object accessed with `Fiber.current`.
Current performance is terrible. `TLS.get` should be around 1ns. `Fiber.current` is around 20 ns. Mutex-protected get is nearly 60 ns at present; should be ~17 ns.
Idea is to store FLS data in per-fiber runtime data structures. Should have a way for independently-developed systems to co-operate on FLS, not all have to use (e.g.) Picos.

Vesa's slides: [Support for FLS in the OCaml runtime
](https://gist.github.com/polytypic/6bbb40a8d517e9dfb7ccdcded8abca50)

Discussion: there seems to be an unanswerable performance case. Documentation of this will need to accompany any PR, as there has been pushback about the proliferation of levels of local storage (domain-local, thread-local, fiber-local). We will also need to carefully document the appropriate uses of each, and the hazards of using the wrong one, in the manual and in the relevant `.mli` files.

## GC Pacing

Damien: need to add a mechanism for programmer to advise the GC about allocation of long-lived data (often large collections of long-lived objects). The problem is not symmetric; if you release lots of things, people aren't concerned about accelerating the GC at that point (because the memory is already allocated, and it won't be freed without compaction).
Stephen: even in a ramp, it is often the case that most allocated objects are going to die soon; what changes is how long the surviving objects are going to live.
Nick observes that with an appropriate switch unmarshalling might behave better (for Coq) in OCaml 5 than 4, as in 4 things will often be unmarshalled in the minor heap and then need to be promoted to the major heap, whereas in 5 they can be allocated directly in the major heap and not drive the GC clock forwards.
Damien: For Coq we want to be able to say "all this allocation is long-lived". This shouldn't be set in the unmarshaller, as there are unmarshalling applications for which the unmarshalled data is short-lived (e.g. RPC-style data transfer). In other applications during a "ramp" it's not so black-and-white, it's just that the "mortality rate" goes down markedly during the ramp. So maybe what the GC needs is a knob rather than a switch?

Side-note: the fact that systhreads is in otherlibs, rather than an integral part of the runtime, is an accident of history. It may fairly soon be integrated into the runtime, with some re-architecture to clean up the interface (e.g. the "hooks" may disappear).

## Forthcoming performance changes

Nick spoke briefly about some performance-related changes which are in the works:
- Sadiq has a "sweep optimisation" change, which run-length encodes free blocks in the single pool in the shared heap. This should save a significant amount of sweep time in many workloads (making sweep time proportional to live data, not to heap size, as Stephen points out). There was some discussion of losing prefetching effects on Intel (which optimises equal-stride prefetching); maybe we can hack something in to compensate for this?
- Sadiq also has a change to introduce huge-page-sized pools. This is a simple change, and may improve TLB performance for some workloads, but there's a concern about space overhead (as we may readily get a huge-page-sized pool for a sizeclass with hardly any live blocks).
- Stephen's "markdelay" change is done on the `flambda-backend` repo; Nick is looking at upstreaming it.
- Sadiq and Nick have a change in the works for `flambda-backend`, with chunk-allocated pools for the shared heap and a new compactor algorithm - due to Leo - which preferentially retains larger chunks. This should deliver better TLB performance, although it's not yet tailored for any particular chunk size.

## AOB

### The write barrier

Vesa: can we speed up the write barrier?
Stephen: Damien had a branch for this, inlining the fast cases, which was shelved some time ago because programs weren't spending as much time in the write barrier as we had thought. If you have example programs which are problematic, we could resurrect it.
Vesa: I have benchmarks.
Stephen: There's an unavoidable cost when recording long-lived references to new objects (the remembered set: a valuable service). But we can certainly speed up the check paths (when the write barrier decides that it doesn't have to record anything).
Damien: we've never had an "erase" primitive.
Stephen: We could often statically detect, in the compiler, when we're writing an immediate value, and avoid `caml_modify` then.
Vesa: I've also measured poor performance for atomic operationsm such as compare-and-set with integer values only.
There's general agreement that cases like that should often be compiled out, and certainly shouldn't go out to `caml_modify`.

### Prefetching in mark/sweep

Tim: Is the prefetching code in mark and sweep phases cross-architecture?
Stephen: it should be; it uses compiler builtins.
Discussion concludes that apparently it's not, but we should make it so.
