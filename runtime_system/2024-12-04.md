# OCaml Runtime/GC Meeting Notes from 2024-12-04

Approximately every six weeks we have an informal meeting between OCaml developers with a focus on the language runtime. The meetings are for sharing understanding and ideas, not for formal planning purposes. This document is notes from the meeting held on 2024-12-04 at 10:00 UTC.(10:00 Cambridge, 11:00 Paris), attended by Damien Doligez, Tim McGilchrist, Antonin Decimo, Fabrice Buoro, and Jan Midtgaard.

## Damien on GC: strings vs bytearrays

Damien has been having fun with GNUplot. Graphing runtime against space used, for a program of interest to Jane Street. The program has lots of big strings, and has performance problems in 5.2 because the GC goes crazy, working very hard without gaining space because there's no space to gain. Stephen suggested bytearrays instead of big strings, and indeed these have different performance characteristics. This is a mystery: the bigstring version seems to hit a wall as space usage is increased, where run time stays constant. The bytearray version does not exhibit this behavior.

## Nick on mark-delay

Progress upstreaming Stephen Dolan's mark-delay refinement to the major GC has been delayed by finding several defects with CI and reviews. Firstly, a problem with pacing code which causes crashes on Win32 and performance issues on other platforms. Secondly, a problem with orphaned ephemerons, detected by the multicore tests: it was possible for ephemerons to be adopted on the same cycle on which they are orphaned, which triggers an assertion. Thirdly, a problem of failing to make progress with the major GC if no minor allocation takes place. See [#13580](https://github.com/ocaml/ocaml/pull/13580) for some pretty pictures made with pyplot. The fixes to these have been made to `flambda-backend` but #13580 itself is still pending as there is an unresolved problem with orphaned finalisers.

What also arose in review is a bug in ephemeron marking for ephemerons which have lazy values as keys. See [#13632](https://github.com/ocaml/ocaml/pull/13632). Stephen and Nick went too far in proposing a fix, as Damien pointed out on the PR. A small fix is necessary but it's probably better, pointed out by Damien, to prohibit the use of lazy values as ephemeron keys, which breaks the semantics of the language (a lazy value doesn't really have an identity, as it can be short-circuited by the runtime at any point).

## Jan in Paris

Jan has been in Paris, debugging a multicore crash on MacOS, on Apple Silicon only, in a lengthy debug session with Olivier. The crash happens in a test with Jan's usual test shape: a sequential prefix then two domains in parallel. Bug seems to happen in connection with domain termination, with other domains doing speculative marking. One domain at the beginning of a cycle, the other, doing speculative marking, is at the end.

## Tim

Getting frame pointers working for RISC-V and s390. Miod got a fair way with RISC-V, which has a strange layout. s390 is a bit more standard as an architecture. POWER is next, but POWER backend doesn't have CFI information; have to add that before we can debug frame pointers, so that's probably a 2025 job. Started writing a manual section on using `perf` for profiling. One main reason to want frame pointers on all platforms is that it enables reliable `perf` use, better than DWARF. Name-mangling is on the back burner; did a port of C++ name-mangler to OCaml but that's probably not what we want.
