### Modular explicits

- new kind of identifiers, `Unscoped.t`, for module names bound in module-dependent functors
- they can be unified, but there is also a separate mechanism to assume equalities between them in the environment
- subtyping between Tarrow and Tfunctor (and conversely) is a bit tricky

Relevant subtyping code starts at

https://github.com/ocaml/ocaml/blob/c76a25229740d38c2d4975ea4267d02cec20255f/typing/ctype.ml#L5618

### Deprecating type aliases

Jacques: the description says that adding the attribute should not make the code fail, only raise warning. But the code does not do this, sometimes it refuses to expand and so it will fail in some cases.

Gabriel: so maybe you want a more conservative approach, where instead of a flag "refuse to expand here" (and warn otherwise), we should have a flag "warn here if you need to expand".

Jacques: if we had a global setting "ignore this deprecation", we could compare the type-checking of examples with and without the expansions prevented.

Gabriel: maybe in practice it would be enough to warn reliably in unification and in module signature matching, and remain silent on other expansions.

Florian: I think it's okay if the warning has some false positives.

Jacques: in unification does not expand if it does not need to. It might expand too much in some cases.

Richard: I think that things can go wrong if you expand more than necessary.

Gabriel: instead of warning on expansion, we could mark the expanded types as "bad". So `type t = int [@@deprecated]` gives you a `bad_int`, maybe using the scope?

Samuel: but we don't want to allow to unify two bad int together without warning.

Richard: we could have a builtin type `'a deprecated`, and that expansion fails.
